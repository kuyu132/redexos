# 双平台开发与故障定位方法

更新：2026-10-26。本文规定接下来的实验、证据和验收方式；未执行的实验不代表已实现能力。当前状态见 [移植计划的功能矩阵](porting-plan.md#当前功能矩阵)，历史产物和结果索引见 [verification.json](verification.json)。

## 依据与项目决策

系统移植仍需逐个修复缺陷，但每次实验应检验明确的假设、缩小原因范围，并为后续版本留下可重复的检查。修改代码、加打印、刷卡和拍照本身都不是修复证据。

以下实践来自公开的一手资料，具体分阶段方式和数量门槛是本项目的工程选择：

- [U-Boot 调试指南](https://docs.u-boot.org/en/latest/develop/driver-model/debugging.html)建议先在 sandbox 中开发可隔离功能，并启用早期调试 UART，必要时使用硬件调试器。应用到本项目：纯逻辑尽量离板测试，固件和外设路径仍需实机验证；不能假定某款调试器已经支持 Pi 5 的 CPU 调试。
- [Linux 测试指南](https://docs.kernel.org/dev-tools/testing-overview.html)区分内部小单元测试和从用户态验证整项功能的测试。应用到 Redox：借用测试分层的方法，不把 Linux 的 KUnit、KASAN 等工具直接说成 Redox 已有能力。
- [Linux 回归二分指南](https://docs.kernel.org/admin-guide/verify-bugs-and-bisect-regressions.html)要求验证可工作的旧版本和失败的新版本。Pi 5 尚无启动到用户态的成功基线，当前是首次移植故障，不能将诊断 v1–v4 当作已知好坏版本进行回归二分。
- [LAVA 设备接入要求](https://docs.lavasoftware.org/lava/developer/tutorials/new-device-type.html)重视串口、自动复位、可重复部署和可靠的初始状态；[引导测试与恢复](https://docs.lavasoftware.org/lava/introduction/use-cases/bootloader-testing.html)把恢复能力纳入引导测试。当前先复用现有脚本，不增加整套 LAVA 服务；自动供电、串口和恢复路径实际验证后，再考虑无人值守的硬件测试。

## 当前问题的证据边界

已经具备源码和补丁锁定、镜像哈希、QEMU 功能回归、SD 写后校验、失败分区备份与日志提取。这些继续保留。需要补齐的是独立观测通道、同一环境内的受控实验，以及准确的当前状态。

本次故障证据如下：

| 事实 | 可以得出的结论 | 不能得出的结论 |
| --- | --- | --- |
| Pi 5 显示 Redox EFI，传入 DeviceTree，报告 512 MiB 读取完成，首个 RedoxFS 文件头校验通过 | 已越过固件装载 EFI 和初始文件读取阶段 | 整个文件系统、内核和用户态已通过 |
| v3 实卡日志最后是 `FS-CALL`，照片多出 `FS-READ #2 pending` | 屏幕与落盘进度存在差距，需要区分记录日志和内存读取的调用边界 | 第 2 次 SD 数据读取失败，或一定卡在 `Flush` |
| 同一实卡 FAT 内容的副本在 QEMU A76/EL2 下通过用户态验证 | 捕获内容可在该 QEMU/EDK2 环境启动 | Pi 5 固件、内存属性、调用栈和硬件路径没有问题 |
| v4 通过 QEMU 回归并已写卡、校验 | 调用阶段诊断已交付 | Pi 5 故障已修复；目前尚无 v4 实机结果 |

`redox-live.iso` 载入后，`FS-READ` 的数据来自 RAM；但打印这条记录仍可能调用固件向 SD 写日志。因此日志通道自身也在被怀疑的执行路径中。逐条 `Flush` 有利于断电取证，同时会改变 I/O、时序和栈使用；最后一行只缩小范围，不等于故障指令。

## 开发顺序与阶段门槛

保持 ARM64 公共实现、通用驱动、板级资源三层代码结构。QEMU 保持公共代码和用户态回归；两块板的 MMIO、IRQ、DMA、固件交接与外设单独验收。当前实机工作集中在已有 Pi 5；Pi 4B 继续维护构建和离线检查，取得实机后独立验收。

| 门槛 | 最小验证对象 | 放行证据 |
| --- | --- | --- |
| G0 可恢复、可观察 | 固定构建和板卡信息、从上电开始采集、失败介质归档、恢复启动环境 | 原始日志、镜像及固件哈希、恢复操作实际结果；缺失字段写 unknown |
| G1 固件边界 | 小型 EFI 程序分别检查内存分配、FAT 读写、Write/Flush、内存中的 RedoxFS 打开 | 每项开始/返回/错误，重复结果；纯固件测试不启动内核 |
| G2 内核入口 | 最小内核、内存文件系统、单核策略；固件退出和异常级交接 | 最终 DTB 与内存图，入口参数、早期输出、受控异常信息；不使用桌面作为入口测试 |
| G3 用户态 | MMU、异常、GIC、定时器、调度、系统调用、一个最小进程 | 程序输出、系统调用结果、退出状态；同一组合至少 5 次冷启动 |
| G4 板级驱动 | SD、网络、USB、显示逐项加入 | 控制器独立测试、超时/错误恢复；不能用固件 SD 读取替代 Redox SD 测试 |
| G5 开发工作流 | 桌面编辑、保存、编译、运行、调试与重启 | 实际操作和内容校验，再执行至少 4 小时代表性负载；单次通过不表示稳定性验收 |

门槛用于限制完成声明和集成范围，不阻止提前开发独立模块。5 次冷启动和 4 小时负载沿用项目初始门槛，不是行业认证或长期可靠性保证。测试必须记录实际次数、持续时间和全部失败。

## 下一轮实验：先拆开固件、日志和文件系统

先冻结 v3 失败现场和已交付的 v4 候选。v4 的实机结果尚待取得；在结果返回前，可以准备隔离测试，但不叠加多个推测性“修复”并发布下一张混合镜像。每个实验从固定的输入副本开始，原始取证文件保持只读。

| ID / 顺序 | 要回答的问题 | 实验设计 | 判据和限制 |
| --- | --- | --- | --- |
| E0：收集已有 v4 结果 | 停在格式化、Write、Flush、还是它们之外？ | 使用已交付版本，记录版本、最后屏幕阶段、最后 FAT 记录、等待时间和是否重启 | 得到更窄的调用区间；仍不能从最后一条打印确定 PC 或排除诊断自身问题 |
| E1：日志对照 | FAT 日志路径是否影响故障？ | 固定固件、系统载荷和硬件，用同一候选的运行选项比较 FAT 日志开启/关闭；两者保留相同的屏幕或独立 UART 检查点；按 A/B/A 顺序恢复相同初始介质状态 | 只有写日志时失败，说明日志路径、资源或时序相关；不能直接断言固件有 bug。关闭后仍失败，继续查公共路径 |
| E2：独立 FAT 探针 | 脱离 RedoxFS 后固件文件 I/O 是否正常？ | 小型 EFI 测试在专用测试文件中分别做读取、写入、短写处理、Flush、关闭和再次读回；先小负载，再复现原加载量与记录长度 | 精确返回码、写入字节和重启读回校验；若独立失败，可向固件项目提交更小复现；通过不能排除原程序栈/内存布局影响 |
| E3：RAM 文件系统探针 | 不写 FAT 时，RedoxFS 打开路径是否能完成？ | 用固定镜像加载到 RAM，停止 FAT 日志，单独执行生产 RedoxFS 的头环/allocator 打开；与宿主 fixture 和 QEMU 运行比较 | 记录成功/失败和最后操作；宿主与 QEMU 通过只证明各自环境，Pi 5 仍须单独执行 |
| E4：按证据选择 | 是否为栈、ABI、内存属性或异常交接问题？ | 保存实际 SP 和可验证的栈边界、内存图、相关寄存器、匹配的调试符号；根据 E1–E3 选择栈水位/边界或具体调用检查 | 静态大栈帧只是假设线索；扩大栈后通过也需证明边界违规和修复机制，不能靠改大小宣告根因 |

2026-10-26 已实现 E1–E3 的独立 EFI/宿主探针并完成宿主和 QEMU 验证，见 [隔离测试执行说明](boot-isolation.md)。实机 E0–E4 尚无新结果；用户确认 v4 尚未测试。E4 仍是按证据选择的后续设计。优先选能够区分原因、实现代价低的一个实验；若上一实验已给出决定性证据，不机械执行全部列表。同一变量重复三次可作为初筛；出现间歇性后保留全部结果并增加样本，不能挑选成功启动。

另设硬件健康检查：如需排查供电、卡或固件基本兼容性，用独立介质运行该板已知可用的参考系统，记录板修订、EEPROM、供电和 SD 信息。参考系统通过只验证其硬件/软件组合，不验证 Redox 的 UEFI 调用路径；不要为此覆盖失败现场。

## 观测通道与异常现场

当前缺少串口适配器。HDMI 阶段码和 FAT 日志继续作为可用证据，但都有盲区。下一项优先补齐的设备能力是 Pi 5 UART10 到宿主机的串口采集，具体接线见 [实机测试手册](hardware-testing.md#串口连接)。用已验证、带超时的早期 UART 输出，避免日志函数因串口不可用而永久等待。

异常现场应包含当前 EL、对应级别的 ELR/ESR/FAR/SPSR、SP、必要的栈内容及构建 ID，并用匹配符号还原位置；启动交接另保存 DTB、内存图及需要核对的控制寄存器。固件仍在运行时不能未经验证替换其异常向量；先确认向量归属和恢复约定，再实施捕获。

没有异常信息的停顿不能标成 panic。超时只说明未完成；若要取得卡住时的 PC/调用栈，需要可用的固件调试或另行验证的硬件调试能力。UART 本身不提供断点或 CPU 停机能力。Boot Services 结束后，不再调用 UEFI 文件日志服务；内核阶段使用自己的输出或后续持久化机制。

## 自动化分层与现有入口

| 层级 | 覆盖范围 | 当前可复用入口 | 尚需补齐 |
| --- | --- | --- | --- |
| 宿主 | 镜像解析、边界检查、日志短写/失败、资源合同 | `python3 -m unittest discover -s tests -v` | 固定失败 fixture、生产 RedoxFS 独立探针；工具链支持时再增加 sanitizer/fuzz 检查 |
| QEMU | EL1/EL2 启动、异常镜像、日志持久化、公共 ARM64 和用户态 | `verify-boot-diagnostics.py`、`verify-boot-log.py`、`verify-qemu-*.py` | 新隔离模式的回归；保留现有真实桌面工作流 |
| 实机 | 固件契约、MMIO/IRQ/DMA、冷启动 | `collect-serial.py`、`verify-board.py`、`collect-boot-logs.py` | 串口设备、实际探针运行、最终 DTB/内存图；现有板上自动测试尚未跑通 |
| 持续硬件测试 | 部署→启动→测试→收集→恢复 | 复用写卡/快照脚本和 `verify-board.py` 的电源命令接口 | 实际供电控制、可靠介质部署和恢复验证；当前仍需人工插卡/断电 |

脚本均位于 `scripts/`；带镜像、串口或输出参数的调用以对应测试文档和 `--help` 为准。修改纯日志逻辑时跑相关宿主与引导回归；涉及内核、libc、文件系统时，再运行受影响的持久化/网络/开发回归。不因只修改文档重跑整套构建。

每个硬件测试区分：测试断言失败、启动超时、采集/供电等基础设施失败。通过要求本轮新的启动 ID、预期输出、真实退出状态或数据校验，旧日志或旧标记不能算通过。恢复后再次运行健康检查；恢复到 v3/v4 只恢复实验状态，并不意味着恢复到可用 Redox 系统。

## 缺陷记录与关闭条件

每个问题记录以下字段。实验日志和原始结果不可用后来的成功覆盖；当前能力矩阵只汇总有证据的组合。

```text
issue_id / experiment_id:
problem_and_expected_behavior:
board_revision_RAM_power_EEPROM: unknown 项明确保留
firmware_and_settings / final_DTB_hash:
source_revisions / patch_hashes / toolchain / build_flags:
image_hash / symbols / initial_media_snapshot:
hypothesis_and_alternatives:
single_changed_factor / expected_results_for_each_hypothesis:
procedure / timeout / repetition_count:
actual_results / raw_logs / exception_or_hang_evidence:
conclusion: supported | rejected | inconclusive
next_experiment:
```

故障关闭需要：明确失败条件和机制；有失败复现或足够的实机现场证据；最小修复在原失败环境通过；受影响层的回归通过；保留恢复路径。可行时做旧版失败/修复通过的负对照。无法安全复现或没有机制证据时，记录“未再出现”或“暂时绕过”，不写“根因已修复”。诊断能力、功能实现、实机通过和稳定性通过分别登记。

当前首先交付的是能区分 FAT 日志、固件 I/O 和 RAM 文件系统处理的最小测试，以及明确的实验记录；取得实机证据后再选择修复。QEMU 桌面和开发能力继续作为已有回归基线维护。
